การทำ Data Normalization และวิเคราะห์ Functional Dependency (204321)

ฉบับที่ 5: แต่ละ relation เก็บเฉพาะ attribute ของตัวเอง และอ้างถึง relation อื่นด้วย Foreign Key เท่านั้น (ไม่พ่วง attribute ของ relation อื่นมาด้วย)

เกณฑ์การอธิบายตามข้อกำหนดของอาจารย์:
  • กรณีที่ 1 (Relation อยู่ใน 3NF ตั้งแต่แรก): อธิบายพิสูจน์ว่าทำไมถึงผ่านเกณฑ์ 1NF, 2NF และอยู่ใน 3NF ตั้งแต่แรก
  • กรณีที่ 2 (Relation ไม่อยู่ใน 3NF): ดำเนินการแตกตาราง (Decompose) ให้อยู่ใน 3NF พร้อมอธิบายว่า ทำไมถึงไม่อยู่ใน 1NF, 2NF และ 3NF ในแต่ละขั้นตอนที่ดำเนินการ

หลักการ: relation หนึ่งเก็บข้อมูลของ entity / relationship เดียว

ฉบับก่อน (v4) เริ่มจากตารางที่พ่วงข้อมูลของ relation อื่นเข้ามาด้วย เช่น ENROLL_1 มีชื่อและอีเมลของนักศึกษา และ SCORE_1 มีรายละเอียดของควิซ ฉบับนี้เริ่มจาก relation ที่ได้จากการแปลง ER diagram (ER-to-Relational Mapping) โดยตรง แต่ละ relation มีแค่ attribute ของตัวเอง และอ้างถึง relation อื่นด้วย Foreign Key เท่านั้น

ตัวอย่าง: relation การลงทะเบียน

v4 (พ่วง attribute ของ STUDENT มาด้วย)

ENROLL_1(student_id, course_code, s_first_name, s_middle_name, s_last_name, s_avatar_url, s_created_at, s_auth_user_id, s_email, s_password, e_section, e_status, e_joined_via, e_created_at)

v5 (มีแค่ FK)

ENROLLMENTS_1(student_id, course_code, section, status, joined_via, created_at)

student_id และ course_code ยังต้องอยู่ เพราะเป็น FK ที่บอกว่า "นักศึกษาคนไหนลงวิชาไหน" และเป็นฝั่งซ้ายของ FD ส่วนชื่อ อีเมล และรหัสผ่านของนักศึกษาดูได้จาก STUDENTS_1 และ AUTH_USERS_1 โดย join ผ่าน FK

ผลที่เปลี่ยนไปจาก v4
Relation ใน v4attribute ที่พ่วงมาจาก relation อื่นปัญหาที่เกิดใน v4v5
ENROLL_1ข้อมูลของ STUDENT และ AUTH_USERpartial dependency student_id → s_first_name, … และ transitive dependency s_auth_user_id → s_email, s_passwordENROLLMENTS_1 อยู่ใน 3NF ตั้งแต่แรก
SCORE_1ข้อมูลของ QUIZpartial dependency quiz_id → quiz_name, full_mark, …SCORES_1 และ QUIZZES_1 อยู่ใน 3NF ตั้งแต่แรก
TEACHERS_1email, password ของ AUTH_USERtransitive dependency teacher_id → t_auth_user_id → t_email, t_passwordTEACHERS_1 อยู่ใน 3NF หลังแปลงเป็น 1NF

partial และ transitive dependency ใน v4 เกิดจาก attribute ที่พ่วงมาทั้งหมด เมื่อไม่พ่วงแล้ว ขั้นที่ยังต้องทำจริงเหลือแค่ UNF → 1NF คือแยก composite attribute (Name) และ multivalued attribute (Login_provider) ที่มาจาก ER diagram หลังจากนั้นทุก relation ผ่าน 2NF, 3NF และ BCNF

เทียบกับเกณฑ์ของอาจารย์:

  • กรณีที่ 1 (อยู่ใน 3NF ตั้งแต่แรก): COURSES_1, QUIZZES_1, ENROLLMENTS_1, SCORES_1, UPLOADS_1
  • กรณีที่ 2 (ไม่อยู่ใน 3NF): AUTH_USER_0, STUDENT_0, TEACHER_0 ไม่ผ่านตั้งแต่ 1NF และแก้ในขั้นที่ 1 แล้วผ่าน 2NF, 3NF ต่อได้ทันที

แท็บถัดไปจะไล่ทีละขั้น 1NF → 2NF → 3NF แต่ละขั้นมีตารางตรวจรวม แล้วตามด้วยรูป FD และเหตุผลว่าทำไมแต่ละ relation อยู่ในขั้นนั้น
